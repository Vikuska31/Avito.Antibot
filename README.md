# Avito.Antibot
# Bot Detection Challenge

## 1. Описание решения

Задача — для каждой `cookie_id` оценить вероятность того, что трафик относится к автоматизированным сервисам сбора данных.

Целевая переменная:

* `target = 1` — трафик известных автоматизированных сервисов;
* `target = 0` — трафик, отнесённый к человеческому.

Модель должна возвращать значение `score` от 0 до 1. Чем выше `score`, тем выше вероятность принадлежности cookie к положительному классу.

Основная метрика соревнования — **Precision при Recall ≥ 70%**.

---

## 2. Используемый подход

Решение состоит из следующих этапов:

1. Загрузка и проверка исходных данных.
2. Построение поведенческих признаков по `events.csv.gz`.
3. Объединение признаков с `train.csv` и `test.csv`.
4. Временная валидация.
5. Обучение модели CatBoost.
6. Усреднение предсказаний нескольких моделей с фиксированными random seed.
7. Обучение финальной модели на всех доступных обучающих данных.
8. Формирование и проверка `submission.csv`.

Все признаки строятся только по событиям, которые попадают в соответствующее суточное окно наблюдения:

`window_start_ts <= event_ts < window_end_ts`

Таким образом, события за пределами окна не используются.

---

## 3. Построение признаков

Основная идея — описать поведение каждой cookie внутри её суточного окна.

### Общие поведенческие признаки

Для каждой `cookie_id` рассчитываются:

* общее количество событий;
* количество событий разных типов;
* количество уникальных объявлений;
* количество уникальных категорий;
* количество уникальных локаций;
* количество уникальных продавцов;
* количество уникальных поисковых запросов;
* количество различных страниц поиска;
* доля повторяющихся действий;
* отношение количества уникальных объектов к общему количеству событий.

### Временные признаки

Используются:

* продолжительность активности cookie;
* время между первым и последним событием;
* минимальный, средний и медианный интервал между событиями;
* количество очень коротких интервалов;
* интенсивность событий;
* количество событий в разных временных частях окна;
* признаки активности отдельными временными блоками.

Эти признаки позволяют отличать равномерное человеческое взаимодействие от более регулярной или интенсивной автоматизированной активности.

### Последовательность действий

Дополнительно учитываются:

* количество переходов между различными типами событий;
* повторяемость одинаковых действий;
* количество последовательных событий одного типа;
* частота различных комбинаций действий.

### Поиск

Для поискового поведения используются:

* количество поисковых событий;
* количество уникальных запросов;
* количество страниц выдачи;
* максимальная глубина просмотра;
* количество повторных поисков.

### Работа с объявлениями

Используются:

* число просмотренных объявлений;
* число уникальных объявлений;
* число категорий;
* число локаций;
* повторные просмотры одних и тех же объявлений.

### User-Agent и платформа

Из `user_agent` извлекаются компактные признаки, описывающие:

* тип устройства/клиента;
* браузерные признаки;
* платформу.

Сырые длинные строки User-Agent напрямую в модель не передаются.

### Движения курсора

Для событий, где доступны `pointer_x` и `pointer_y`, рассчитываются агрегированные признаки движения курсора:

* количество наблюдений координат;
* диапазон координат;
* расстояния между последовательными точками;
* средняя интенсивность движения.

---

## 4. Обработка пропусков и данных

Пропуски обрабатываются в процессе построения признаков.

Для количественных агрегатов отсутствие события соответствующего типа означает нулевое значение.

Для категориальных признаков используется специальное значение для отсутствующего значения.

Дубликаты событий не создают дополнительные признаки сверх фактически присутствующих записей.

---

## 5. Baseline

В качестве baseline использован простой набор признаков, аналогичный минимальному решению из `quickstart`:

* количество событий;
* количество уникальных событий/действий.

Для baseline используется Random Forest.

Его задача — показать качество простой модели и дать точку сравнения с расширенным feature engineering.

Константный ответ даёт:

**Precision@Recall≥0.70 = 0.09391**

---

## 6. Основная модель

После построения расширенного набора признаков используется **CatBoostClassifier**.

CatBoost выбран потому, что он хорошо работает с табличными данными и позволяет удобно учитывать категориальные признаки.

Используются фиксированные random seed:

* `0`;
* `42`;
* `123`.

Финальный `score` получается усреднением предсказаний трёх моделей.

Такое усреднение уменьшает зависимость результата от случайности конкретного запуска.

---

## 7. Валидация

Случайное разбиение train-выборки не используется как основная схема, поскольку данные имеют временную структуру.

Для оценки используется **временная валидация**:

* более ранние дни используются для обучения;
* более поздние дни — для проверки.

Это ближе к реальному сценарию соревнования, где тестовая выборка соответствует более позднему временному периоду.

Для оценки используется именно целевая метрика соревнования:

**Precision при Recall ≥ 70%**

Дополнительно могут рассчитываться PR-AUC и ROC-AUC.

---

## 8. Результат

На проверочной выборке получен результат:

**Precision@Recall≥0.70 = 0.81407**

Для сравнения:

**константный baseline = 0.09391**

Результат является локальной оценкой на отложенной временной части train и не использует разметку тестовой выборки.

---

## 9. Формирование submission

Файл `submission.csv` содержит ровно две колонки:

```text
cookie_id
score
```

Для каждой `cookie_id` из `test.csv` присутствует ровно одна строка.

Перед сохранением выполняются проверки:

* количество строк совпадает с `test.csv`;
* `cookie_id` уникальны;
* отсутствуют лишние cookie;
* отсутствуют пропущенные cookie;
* все значения `score` находятся в диапазоне `[0, 1]`.

Порог классификации в submission не используется. Отправляется непрерывный `score`, после чего проверяющая система самостоятельно выбирает порог для расчёта Precision при Recall ≥ 70%.

## 10. Воспроизводимость

Для воспроизведения результата необходимо использовать:

* Python 3.13;
* фиксированные random seed;
* исходные файлы из задания;
* Jupyter Notebook `bot_detection_solution.ipynb`.

Структура проекта:

```text
project/
├── data/
│   ├── train.csv
│   ├── test.csv
│   └── events.csv.gz
│
├── bot_detection_solution.ipynb
└── README.md
```

Ноутбук содержит весь процесс получения результата: от загрузки данных и построения признаков до формирования `submission.csv`.

Внешние API и большие языковые модели не используются.

Ручная разметка тестовой выборки и хардкод ответов для отдельных `cookie_id` не используются.

---

## 11. Ограничения решения

Основное ограничение — модель использует только информацию, доступную внутри предоставленного суточного окна.

Кроме того, локальная временная валидация не полностью совпадает со скрытой тестовой выборкой, поэтому локальный результат не гарантирует такое же значение метрики на leaderboard.

Тем не менее временное разбиение позволяет избежать основной проблемы случайной валидации — использования данных из будущего при оценке модели.
